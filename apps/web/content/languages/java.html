What people actually paste

Enterprise-shaped code: a class with @Override annotations, a private static final constant, generics on both sides (Map<String, List<Order>>), a checked exception in the signature (throws IOException), and a stream chain with lambdas. Annotation proliferation is the Java-specific visual problem — three stacked @ lines above a method push the actual signature out of the reader's first glance. Also common: imports blocks, which are eleven identical lines of low information that eat the card.

How auto-detection behaves

Java is rule 5, after the four curly-brace-adjacent languages that have their own signatures. Triggers: a line starting public class, public static or public void, and System.out.print. The hole is modifier-free code: class OrderService { without public, a record (record Point(int x, int y) {}), or a snippet that begins with @Override all miss every trigger and land on the typescript default. Since plenty of real Java is package-private, this is not a rare edge. Conversely, public static in a C# snippet will be typed as Java, because Java's rule comes first.

Theme that reads best

material-theme-darker for dark: annotations, keywords and types get distinguishable hues without the high-saturation noise, which matters when there are three annotations stacked. catppuccin-latte is the light option; its soft annotation colour keeps the @ lines from shouting louder than the method name.

Three tips

  • Crop the import block. Eleven import java.util.* lines cost a third of a 16:9 card and tell the reader nothing; one representative import is enough.
  • Put the annotation on the line above and let the signature own its line — Java cards are usually read top-left first, and a merged @Override public void run() buries the method name.
  • At font size 16, a Map<String, List<Order>> declaration plus a stream chain overruns 100 columns; split the chain at .stream() rather than shrinking the font.
